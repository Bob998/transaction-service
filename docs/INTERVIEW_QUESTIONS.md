# 金融交易系统面试问题库

这份题库按“先给结论，再讲原理，最后落到项目证据”的方式组织。面试时不要逐字背诵，先用两三句话回答核心，再根据追问展开。

## 一、交易、数据库与一致性

### 1. 幂等键解决什么问题？

幂等键把多次技术请求识别为同一个业务意图，避免客户端超时重试、网关重放或用户重复点击产生多笔交易。它解决的不是“请求只能到达一次”，而是“请求即使到达多次，业务结果也只生效一次”。

本项目采用三层保障：先查Redis短期结果缓存，再查PostgreSQL，最终依赖`idempotency_key`唯一约束处理并发竞争。相同Key且请求内容一致时返回首次结果；相同Key但金额、币种或描述不同则返回409，防止调用方错误复用Key。Redis只是性能优化，即使缓存丢失，数据库仍能保证正确性。

需要注意：幂等范围必须定义清楚，Key通常应由上游按业务操作生成，并配置合理生命周期；不能用随机Key重试，否则每次都会被视为新业务。

### 2. 为什么“先查询不存在，再插入”不能保证幂等？

因为查询和插入之间存在竞态窗口。两个并发请求可能同时查到“不存在”，随后都尝试插入。如果数据库没有唯一约束，就会产生重复数据。

正确做法是把数据库唯一约束作为最终原子裁决：本项目插入使用`ON CONFLICT (idempotency_key) DO NOTHING`。只有一个请求插入成功，失败请求重新读取已存在交易，再校验请求内容并返回原结果。应用层预查询可以减少冲突，但不能替代数据库约束。

如果面试官追问分布式锁，可以回答：锁能降低并发冲突，但锁可能超时、续租失败或Redis不可用，所以不能成为唯一正确性保障。

### 3. 为什么交易系统要显式设计状态机？

状态机把交易生命周期和合法转换集中定义，避免业务代码在各处直接修改字符串状态。它能阻止跳过必要阶段、终态回退、重复确认和取消已成功交易等错误。

本项目主状态为：

```text
CREATED → RISK_APPROVED → PROCESSING → SUCCEEDED / FAILED / CANCELLED
```

每个操作同时检查当前状态和数据库版本。例如只有`RISK_APPROVED`才能进入`PROCESSING`，`SUCCEEDED`是终态，不能再次成功或取消。非法转换返回409，并留下审计记录。

状态机仍不能单独解决并发：两个线程都可能在内存中看到同一合法状态，因此还要配合数据库条件更新和乐观锁。

### 4. 乐观锁如何阻止并发重复确认？

乐观锁假设冲突不是常态，不提前占有数据库锁，而是在更新时验证数据是否仍是读取时的版本：

```sql
UPDATE payment_transaction
SET status = ?, version = version + 1
WHERE transaction_no = ? AND version = ?
```

两个请求都读取`version=0`时，只有一个能更新成功并把版本改为1；另一个影响行数为0，系统把它识别为并发冲突，而不是再次执行业务副作用。

本项目用并发集成测试让两个线程同时确认同一交易，断言只有一次成功。注意不要把“影响0行”一律解释为版本冲突，还应区分记录不存在、状态不合法等情况。

### 5. 乐观锁、悲观锁和串行化应该怎样选择？

乐观锁适合冲突概率较低、读多写少、事务需要尽量短的场景，优点是不长期持锁，缺点是冲突后需要失败或重试。交易状态更新通常很短，因此本项目采用乐观锁。

悲观锁如`SELECT ... FOR UPDATE`适合冲突高且必须串行修改的场景，但会增加等待、死锁和连接占用风险。数据库串行化隔离级别提供更强保证，但吞吐成本更高，也可能产生序列化失败。

不能只按“金融系统必须用悲观锁”判断。应根据冲突率、事务长度、可否重试、吞吐目标和数据库压力选择，并通过指标观察冲突率和等待时间。

### 6. `@Transactional`在什么情况下回滚？传播行为有什么意义？

Spring默认对`RuntimeException`和`Error`回滚，对受检异常默认不回滚；可以通过`rollbackFor`调整。如果异常被业务代码捕获后不再抛出，代理看见的是正常返回，事务也会提交。

常见传播行为：

- `REQUIRED`：有事务就加入，没有就创建，是默认值；
- `REQUIRES_NEW`：挂起外层事务，创建独立事务；
- `NESTED`：在支持时使用保存点，局部回滚；
- `SUPPORTS`：有事务就加入，没有就非事务运行；
- `MANDATORY`：必须在已有事务中运行，否则报错。

本项目使用`REQUIRED`保证交易状态、账务、审计和Outbox按业务边界原子提交。`REQUIRES_NEW`不能随意用于“保证日志一定成功”，否则可能出现主交易回滚但独立日志却显示成功的语义冲突。

### 7. Spring事务为什么会自调用失效？

常规Spring事务基于代理。外部对象调用Bean的事务方法时，请求先经过代理，代理开启事务后再调用目标对象；同一个对象内部通过`this.method()`调用另一个事务方法，会直接进入目标方法，绕过代理，因此新的传播配置不会生效。

常见解决方式是把不同事务边界拆到独立Spring Bean，由外部代理调用；也可以注入自身代理，但可读性和循环依赖风险更高。不要把方法改成`public`就认为问题解决，关键是调用是否经过代理。

此外，非Spring管理对象、`private`方法、构造阶段调用，以及异步线程切换，也可能使原事务上下文失效。

### 8. Transactional Outbox解决了什么问题？

Outbox解决“数据库提交和消息发送无法处于同一个本地事务”的双写问题。业务事务不直接把“数据库成功”和“Kafka成功”绑在一起，而是在同一个PostgreSQL事务中同时写业务数据和Outbox事件。只要事务提交，事件就一定留在数据库里等待发布；事务回滚，两者一起消失。

后台Publisher认领`PENDING`事件，发送Kafka，成功后标为`PUBLISHED`，失败则记录次数、错误和下次重试时间。本项目实际验证过Kafka不可用时事件回到`PENDING`，恢复后最终发布。

Outbox提供的是“业务数据和待发送意图原子保存”，不是端到端Exactly Once。

### 9. Outbox带来了哪些新问题？

Publisher可能在“Kafka已收到、数据库尚未标记PUBLISHED”时崩溃，恢复后会再次发送，所以消息仍可能重复。消费者必须幂等，不能依赖Producer绝不重复。

Outbox还会带来发布延迟、表膨胀、热点扫描、多实例并发认领、重试风暴和积压监控等问题。本项目通过状态、`attempt_count`、`locked_at`、`next_attempt_at`以及超时锁回收管理发布过程，并通过消费者处理表去重。

生产中还需要归档或清理历史事件，监控最老未发布事件年龄，而不仅看PENDING数量。

### 10. 为什么索引设计为`(currency, created_at DESC)`？

目标查询是按币种等值过滤，再按创建时间倒序取最近若干条：

```sql
WHERE currency = ? ORDER BY created_at DESC LIMIT 20
```

复合索引先放等值过滤列`currency`，再放排序列`created_at`，数据库可以直接从对应币种的索引区间按目标顺序读取前20条，避免全表扫描和Top-N排序。本项目执行计划从顺序扫描约6.3ms降为索引扫描约0.2ms。

索引不是越多越好：每个索引都会增加写放大、存储和维护成本。还要考虑选择性、最左前缀、覆盖查询、数据量和真实执行计划。

## 二、自动化测试

### 11. 单元测试、集成测试和端到端测试的边界是什么？

单元测试只验证一个类或一段领域逻辑，依赖通常用Mock替代，执行快、失败定位准。集成测试验证多个真实组件的协作，例如Spring事务、MyBatis、PostgreSQL唯一约束和Redis Lua。端到端测试从HTTP入口经过完整应用栈，验证调用方真正看到的行为。

本项目中，状态机和路由评分适合单元测试；乐观锁、事务回滚和Outbox适合集成测试；创建—确认—处理—支付—查询适合API或端到端测试。

测试金字塔不是要求固定比例，而是让大量快速测试覆盖分支，少量高价值真实测试覆盖框架和基础设施边界。

### 12. Mockito和WireMock有什么区别？

Mockito在JVM进程内模拟Java接口或对象，适合隔离Repository、Gateway接口并验证调用参数、次数和异常分支。它不经过HTTP序列化、连接、超时或状态码处理。

WireMock启动一个可控制的HTTP服务，模拟第三方支付通道的成功、4xx/5xx、延迟、断连和异常响应，因此能验证HTTP客户端配置、JSON协议、超时和错误映射。

本项目用Mockito测试服务编排，用WireMock验证支付通道超时和第三方异常。若只用Mockito模拟HTTP客户端，就无法证明真实网络边界的处理正确。

### 13. Testcontainers解决了什么问题？

Testcontainers在测试期间自动启动真实版本的PostgreSQL、Redis等容器，测试结束后清理。它避免依赖开发者本机预装数据库，也避免H2与PostgreSQL在JSONB、时间类型、锁和SQL语法上的差异。

本项目的Flyway迁移会在临时PostgreSQL上完整运行，所以测试同时验证了建表脚本、MyBatis SQL和事务行为。CI只要有Docker就能获得与本地一致的环境。

代价是启动较慢、需要容器运行时，镜像拉取也可能受网络影响，因此应复用容器、合理划分测试套件，并保留快速单元测试层。

### 14. 如何用测试证明交易不会被重复确认？

测试需要真正制造并发，而不是顺序调用两次。步骤是：准备同一笔`CREATED`交易，让两个线程在屏障处同时开始确认，两边都读取相同版本，然后统计成功和冲突结果。

最终应同时断言：数据库状态只转换一次、version只增加一次、只产生一次对应审计和Outbox副作用，而不是只断言某个线程抛异常。

如果测试偶尔通过、偶尔失败，通常说明并发起点不可控或断言依赖时序。可使用`CountDownLatch`、独立事务和真实数据库增强确定性。

### 15. 如何验证事务真的回滚？

在被测事务中先写业务数据和Outbox，再故意抛运行时异常。调用结束后必须从事务外重新查询，确认两张表都没有记录。如果在同一个持久化上下文里断言，可能被一级缓存或未提交状态误导。

还应测试异常被捕获、受检异常和异步调用等边界，确认它们符合预期回滚策略。本项目的回滚集成测试使用真实PostgreSQL验证业务和事件要么都提交，要么都不提交。

测试方法上不要给测试本身加一个最终统一回滚的事务来掩盖真实提交结果。

## 三、Redis与Kafka

### 16. 为什么Redis不能作为最终账本？

Redis适合低延迟计数、限流、滑动窗口和短期缓存，但数据可能过期、淘汰、主从切换时丢失，集群也可能暂时不可用。即使开启AOF，也不等同于具备完整金融账本的约束、审计和查询能力。

本项目用Redis做请求限流、通道额度前置控制、风控窗口、路由缓存和幂等结果缓存；交易、账务、审计和对账最终写入PostgreSQL。Redis不可用时，能安全回源的功能降级到数据库，不能安全放行的额度或风控场景选择失败关闭。

核心原则是：缓存可以丢，最终事实不能丢。

### 17. Lua脚本为什么能保证Redis操作原子性？

Redis在执行Lua脚本期间不会穿插执行其他命令，因此脚本中的“读取—判断—修改”整体具有原子性。例如额度控制不能先`GET`再由客户端判断后`INCRBY`，否则两个请求可能同时通过检查并超额。

Lua适合把限额检查、计数更新和TTL设置合并到一次服务器端执行，减少网络往返和竞态。但脚本不能执行过久，否则会阻塞Redis事件循环；集群模式下涉及的Key还必须落在同一个Hash Slot。

Lua保证的是单个Redis实例内的原子执行，不保证数据库与Redis之间的分布式事务。

### 18. 缓存击穿、穿透和雪崩有什么区别？

- 击穿：一个热点Key失效，大量请求同时回源；
- 穿透：持续查询本来不存在的数据，每次都绕过缓存；
- 雪崩：大量Key同时失效或Redis整体故障，回源流量集中爆发。

击穿可用短互斥锁、请求合并、逻辑过期和热点预热；穿透可缓存空值、参数校验或Bloom Filter；雪崩可随机化TTL、分批预热、限流熔断和容量隔离。

任何方案都要保护数据库，并设计Redis不可用时的降级。分布式锁过期后仍可能有多个线程回源，所以数据库必须能承受受控流量。

### 19. Kafka生产端怎样降低丢消息风险？

业务侧先用Transactional Outbox避免“数据库成功但消息未保存”。Publisher发送Kafka时等待Broker确认，生产环境通常配置`acks=all`、合理重试和幂等Producer；Broker侧需要足够副本和`min.insync.replicas`配合。

发送失败不能只写日志，应保留Outbox状态、错误原因和下次重试时间，并监控积压和最老事件年龄。即使`send()`返回成功，也仍存在应用在更新Outbox状态前崩溃导致重复发送，因此消费者幂等不可省略。

可靠性的完整链路是：本地原子保存、Broker持久化、副本、可重试发布、幂等消费和可观测性共同保障。

### 20. Kafka消费者如何处理重复消息？

Kafka常见语义是At Least Once：消费处理成功但Offset提交失败时，消息会再次投递。本项目以`event_id + consumer_group`建立唯一处理记录，并把业务修改、后续Outbox和处理记录放在同一个数据库事务中。

处理前先尝试登记事件；唯一约束冲突表示该消费者组已经完成处理，直接跳过。这样即使Kafka重复投递，业务副作用只发生一次。

不能只在内存Set或Redis中去重，因为进程重启或缓存丢失后记录会消失。去重记录的保留时间还应覆盖Kafka可能重放的时间范围。

### 21. 消费成功但Offset没有提交会发生什么？

消费者重启或Rebalance后会从上次已提交Offset重新读取，因此已经处理的消息会再次到达。这不是Kafka异常，而是At Least Once语义的正常表现。

正确处理方式不是要求“永远不重复”，而是让业务处理幂等，并在业务事务成功之后再提交Offset。如果先提交Offset再处理业务，进程崩溃会造成消息永久跳过；如果业务成功后提交失败，只会导致可处理的重复。

因此金融系统通常宁可重复投递并去重，也不能无声丢失。

### 22. 如何保证交易范围内的消息顺序？

Kafka只保证单分区内有序，不保证Topic全局有序。本项目使用`transactionId`作为分区键，使同一笔交易的事件进入同一分区；不同交易可以分散到多个分区并行处理。

还要避免消费者把同一分区消息交给无序线程池并行执行。重试Topic可能打乱原分区顺序，所以业务状态机仍要校验事件是否符合当前状态，不能只相信到达顺序。

如果要求所有交易全局有序，只使用一个分区会严重限制吞吐。合理目标通常是“同一聚合根有序”。

### 23. 毒消息应该如何处理？

毒消息是无论重试多少次都无法成功的消息，例如格式损坏、缺少必填字段或业务代码不兼容。无限重试会阻塞分区并制造重试风暴。

本项目采用有限重试Topic，超过次数后进入DLQ，保留原Topic、分区、Offset、异常类型和消息内容，同时告警。修复代码或数据后，应通过受控工具重放，并继续依赖消费者幂等避免二次副作用。

DLQ不是垃圾桶。需要负责人、处理时限、查询工具和审计流程，否则消息只是从主链路“消失”到另一个Topic。

### 24. Kafka Lag说明什么？

Lag是分区最新Offset与消费者已提交Offset的差值，表示还有多少消息未被确认消费。但单看数量不足以判断严重程度：流量大时Lag可能高但正在快速下降，流量小时少量Lag也可能已经滞留很久。

应结合流入速率、消费速率、最老消息年龄、处理耗时、失败率和分区分布判断。某个分区Lag异常而其他正常，可能是热点Key或毒消息；全部分区同时增长，可能是消费者容量不足或下游变慢。

扩容消费者数量不能超过分区数获得有效并行度，并且扩容会触发Rebalance，需要控制频率。

## 四、金融业务、风控与可观测性

### 25. 动态支付路由应该考虑哪些因素？

路由不能只选“成功率最高”的通道，应综合硬约束和软评分。硬约束包括币种、金额范围、通道状态、额度和熔断状态；软评分可包含成本、近期成功率、延迟和业务优先级。

本项目先过滤不可用通道，再根据健康度、成本和成功率排序。首选通道熔断后选择备用通道，并记录路由切换指标和审计信息。

成功率要设置最小样本量和时间窗口，避免新通道少量成功就获得过高权重；路由还要支持固定规则、灰度和紧急人工降权。

### 26. 支付请求超时后为什么不能盲目重试？

超时只说明本系统没有及时收到响应，不代表通道没有处理。通道可能已经扣款但响应在网络中丢失，此时直接重试可能造成重复支付。

正确状态应是`UNKNOWN`或处理中，而不是立即标记失败。系统使用稳定的通道请求号或幂等号，优先调用查单接口确认结果；只有明确未受理或通道承诺幂等时才安全重试。长时间未知需要进入补偿和人工处理流程。

本项目故障实验中，通道延迟超过客户端超时后返回`UNKNOWN`，连续故障触发熔断和后续新交易路由切换，而不是盲目重试原支付。

### 27. 为什么选择Aviator做规则风控？

Aviator允许把金额、用户等级、时间窗口次数等条件写成可配置表达式，规则变化不必每次修改Java代码和重新发布。表达式执行轻量，适合基础同步风控。

本项目把业务上下文转换为受控变量集合，由数据库规则决定通过或拒绝，并记录规则、结果和原因。规则引擎只负责计算，最终动作仍由业务服务控制。

安全上不能允许任意对象和函数调用，应使用变量/函数白名单；治理上需要规则版本、审核、测试集、灰度、回滚和命中率监控。规则可配置不等于规则可以无审批直接上线。

### 28. 日终对账解决什么问题？

即使在线事务和消息链路都设计可靠，系统与外部支付通道仍可能因超时、人工操作、文件缺失或通道侧修正产生差异。对账是事后发现和闭环处理这些不一致的机制。

本项目按UTC业务日比较本地成功交易与通道账单，识别金额不一致、本地有而通道缺失、通道有而本地缺失三类差异，生成批次和差异记录。处理差异时记录操作人、说明、状态和审计日志，并防止重复处理。

对账发现差异不等于自动改账。金额和状态修正通常需要明确规则、审批、补偿凭证和可追溯性。

### 29. 为什么P95/P99比平均延迟更重要？

平均值会把少量极慢请求稀释。例如99个请求10ms、1个请求5秒，平均值看起来不算严重，但那1%的用户体验和线程占用已经很差。P99表示99%的请求在该时间内完成，更能反映尾部风险。

尾延迟通常会在高负载、连接池等待、GC、热点锁或慢下游时迅速放大。金融链路由多个串行步骤组成，每一步的尾延迟还会累积。

本项目通过通道人为延迟观察P99上升，再结合通道标签、线程池和连接池定位，而不是只看整体平均值。

### 30. 如何从P99升高定位到具体慢通道？

先确认影响范围：所有API都慢还是支付执行慢；再按`channel`、URI、状态码等标签下钻。如果只有SAFE_PAY的Timer尾延迟上升，就优先检查该通道的调用耗时、超时率和熔断状态。

随后观察应用线程池active/queue、Hikari active/pending、CPU、GC和下游错误。若HTTP工作线程大量等待通道响应，而数据库连接池正常，瓶颈就在下游；若Hikari pending上升，则需要继续分析慢SQL或连接占用。

本项目完整演示了：制造SAFE_PAY延迟→P99上升→三次UNKNOWN→熔断OPEN→AUTO路由切换FAST_PAY→延迟恢复。

### 31. 数据库连接池为什么不能无限增大？

连接池的作用是复用有限数据库连接，不是创造无限吞吐。连接数过少会产生应用等待；过多会让数据库同时处理更多查询，增加CPU竞争、缓存抖动、锁等待和上下文切换，最终整体更慢。

连接池大小应结合数据库最大连接数、应用副本数、查询耗时和目标并发计算，并为管理和其他服务预留连接。还应设置获取超时、连接生命周期和泄漏检测。

本项目把Hikari从10调到20后P99改善，但最终还通过降低压测并发找到稳态边界，说明调优不是单纯“参数越大越好”。

### 32. 生产事故发生时应该先看什么？

先控制影响，而不是立刻猜根因。确认开始时间、影响用户/接口、错误率、延迟和数据正确性；必要时限流、熔断、降级或回滚。然后对齐最近发布、配置变化和依赖故障时间线。

排查通常按RED/USE思路：请求率、错误率、延迟，以及CPU、内存、线程池、连接池和队列饱和度，再下钻数据库、Redis、Kafka和外部通道。每个假设都用日志、指标或线程栈验证。

事故后要保留证据、形成根因和改进项。本项目Kafka KRaft事故复盘不仅记录修复，还记录为什么未提前发现，以及startupProbe、Smoke Test和Outbox积压告警等预防措施。

## 五、Docker、CI与Kubernetes

### 33. 多阶段Dockerfile有什么价值？

构建阶段包含Maven、源码和编译缓存，运行阶段只复制最终Jar和JRE所需内容。这样可以减少镜像体积、攻击面和敏感构建信息，并提高运行环境稳定性。

本项目运行镜像使用非root用户，设置明确的JVM参数和健康检查。非root不能消除所有容器风险，但能降低应用漏洞直接获得容器root权限的影响。

镜像还应固定基础镜像版本、扫描漏洞、使用`.dockerignore`并通过不可变版本标签发布，不能只使用会漂移的`latest`。

### 34. Readiness、Liveness和Startup Probe有什么区别？

Readiness回答“现在能否接收流量”。失败时Pod仍运行，但会从Service Endpoint移除。Liveness回答“进程是否已无法自行恢复”，连续失败会触发重启。Startup Probe用于慢启动阶段，在成功前抑制Liveness和Readiness的过早判断。

本项目实验证明readiness设为失败后，Pod保持Running且重启数不变，但EndpointSlice只保留健康Pod；恢复后重新加入流量。

错误配置Liveness会放大故障，例如数据库短暂变慢就反复重启所有Pod。一般Liveness只检查进程自身是否卡死，Readiness再考虑服务是否具备接流量条件。

### 35. Kubernetes滚动发布怎样工作？

Deployment创建新的ReplicaSet，按`maxSurge`增加新Pod，等待其Readiness通过后，再按`maxUnavailable`逐步减少旧Pod，直到全部替换。过程中Service只把流量发送给Ready Endpoint。

滚动发布能减少停机，但不能自动保证业务兼容。数据库Schema要支持新旧版本并存，事件格式要向后兼容，终止时还需停止接流量、等待在途请求和消费者安全退出。

本项目验证了v1到v2的逐步替换，并观察了新旧Pod数量变化。

### 36. 灰度发布与普通滚动发布有什么区别？

普通滚动发布的目标是最终把所有实例替换成新版本，主要控制替换过程。灰度发布会在一段时间内保留稳定版和新版本，只让少量流量进入新版本，根据错误率、P99和业务成功率决定扩大、暂停或回退。

本项目通过2个stable Pod和1个canary Pod进行流量观察。简单共享Service只能近似按Pod数量分流；生产中常通过Ingress、Gateway或Service Mesh按权重、Header、用户群分流。

灰度的关键不是“同时跑两个版本”，而是有清晰观察指标、停止条件和数据兼容方案。

### 37. 发布失败应该如何回滚？

先停止继续放量，确认旧版本仍有健康容量。使用Deployment历史或明确的旧镜像版本恢复Pod模板，等待Rollout完成，再验证Readiness、错误率、P99和关键业务交易，而不是只看Pod Running。

本项目把镜像改成不存在的版本，观察新Pod`ImagePullBackOff`、旧Pod继续服务，然后执行`rollout undo`恢复。该实验说明滚动策略能保护可用性，但前提是不要把旧副本过早全部删除。

数据库破坏性迁移通常不能靠应用回滚解决，因此Schema变更应采用扩展—迁移—收缩策略。

### 38. HPA的基本工作原理是什么？

以CPU为例，HPA根据当前平均利用率与目标利用率的比例计算期望副本数，大致为：

```text
期望副本 ≈ 当前副本 × 当前利用率 / 目标利用率
```

CPU利用率通常相对于容器`requests.cpu`计算，因此没有合理requests时，HPA可能显示unknown或计算失真。Metrics Server提供资源指标，HPA还包含容忍区间、稳定窗口和扩缩策略，避免频繁抖动。

本项目在安装Metrics Server并设置requests后，通过CPU实验观察副本从2扩到6。HPA只能增加应用容量，数据库、Kafka分区和下游通道仍可能成为瓶颈。

### 39. Kubernetes Secret真的安全吗？

Secret默认只是Base64编码，不等于加密。任何有读取Secret权限的主体都能还原内容；如果etcd未启用静态加密，数据还可能以可读形式存储。

正确措施包括最小化RBAC、启用etcd encryption at rest、限制命名空间访问、定期轮换、避免日志输出，并可接入Vault或云Secret Manager。Secret不应写入Git、Dockerfile或镜像层。

本项目通过部署前脚本创建Secret，并以环境变量注入Pod；这是基础做法，生产环境仍需要外部密钥管理和轮换机制。

### 40. CI质量门禁应该包含什么？

CI把可重复检查变成每次提交的强制流程。本项目执行：编译、72项自动测试、JaCoCo报告、Checkstyle、Compose配置校验、镜像构建和非root检查。任何一步失败都不应进入主分支或发布阶段。

高质量CI还需要缓存依赖、隔离测试数据、保存测试报告和镜像制品、使用不可变Commit SHA标签，并保护主分支。部署流水线应在测试通过后运行，生产发布还可增加人工审批、漏洞扫描、签名和Smoke Test。

CI通过不代表生产一定安全，但它能持续阻止已知错误和工程退化。真正完整的交付证据还包括监控、灰度、回滚和事故响应。

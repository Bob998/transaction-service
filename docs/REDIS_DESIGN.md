# Redis 设计与正确性边界

## 1. 设计目标

Redis 在本项目中负责高频、短期、可重建的数据，用于降低数据库压力和快速拒绝明显异常请求。

```text
客户端
  ↓
限流 / 风控 / 额度保护（Redis）
  ↓
Spring Boot 交易服务
  ├─ Redis：缓存、临时计数、协调
  └─ PostgreSQL：交易事实、状态、审计、Outbox
```

核心原则：

- Redis 不是最终账本；
- PostgreSQL 保存最终交易事实；
- Redis 数据允许过期、丢失和重建；
- 分布式锁不能替代数据库唯一约束和乐观锁；
- Redis 故障时必须根据功能风险选择降级策略。

## 2. Redis Key 设计

| 功能 | Key 格式 | 数据结构 | 生命周期 |
|---|---|---|---|
| 用户请求限流 | `rate-limit:user:{userId}` | String 计数器 | 60 秒 |
| 通道每日额度 | `channel:quota:{channelCode}:{yyyyMMdd}` | String，金额单位为分 | 2 天 |
| 风控滑动窗口时间 | `risk-window:user:{userId}` | ZSET | 窗口长度的 2 倍 |
| 风控滑动窗口金额 | `risk-window:amount:user:{userId}` | HASH | 窗口长度的 2 倍 |
| 通道路由缓存 | `route:channel:{channelCode}` | JSON String | 5 分钟 |
| 幂等结果缓存 | `idempotency:result:{idempotencyKey}` | JSON String | 10 分钟 |
| 分布式锁 | `lock:{resource}` | 唯一 token | 由调用方指定租期 |

Key 使用业务前缀进行隔离，避免不同功能互相覆盖。用户 ID、通道编码和幂等键直接用于定位数据，不使用全量扫描。

## 3. 用户请求限流

接口通过 `X-User-Id` 识别用户。当前项目未接入认证，因此只有请求携带该请求头时才执行限流。

Lua 脚本在一次原子操作中完成：

1. `INCR` 增加计数；
2. 首次访问设置 `PEXPIRE`；
3. 判断是否超过 10 次；
4. 返回当前次数和是否允许。

超过限制时返回：

```text
HTTP 429
code = RATE_LIMIT_EXCEEDED
```

该实现是固定窗口限流。它简单、成本低，但窗口边界附近可能短时间通过两倍流量。更严格的场景可使用滑动窗口或令牌桶。

## 4. 通道额度

通道额度使用 Lua 原子执行：

```text
读取已用额度
→ 判断 used + requested 是否超过 limit
→ 未超限才 INCRBY
→ 首次写入时设置过期时间
```

金额先由 `BigDecimal` 转为最小货币单位 `long`，例如 `10.25` 元转为 `1025` 分，避免 Redis 浮点计算产生金额误差。

并发测试使用 20 个线程各申请 10 元、总额度 100 元，最终恰好 10 次成功，已用额度不会超过 100 元。

通道额度计数是快速保护，不是清算或会计账本。当前额度保护已接入交易创建，在正式支付编排中还需要增加成功扣款、退款和补偿时的额度释放策略。

## 5. 风控滑动窗口

风控使用 ZSET：

- ZSET score：交易发生时间戳；
- ZSET member：交易幂等键；
- HASH field：交易幂等键；
- HASH value：以分为单位的金额。

Lua 原子执行：

1. 删除窗口外的旧记录；
2. 加入当前交易尝试；
3. 统计窗口内交易笔数；
4. 汇总窗口内金额；
5. 判断次数和金额是否超限。

当前规则：

```text
最近 60 秒最多 5 笔
最近 60 秒累计不超过 1000 元
```

被拒绝的交易尝试仍保留在窗口中，因为失败的大额或高频尝试本身也是风险信号。当前风控已接入创建交易流程。

相同幂等键重复提交时，ZSET member 不会增加，因此不会重复累计笔数；HASH 中的金额也只保留一份。

## 6. 通道路由缓存

采用 Cache-Aside：

```text
查询 Redis
  ├─ 命中：返回缓存
  └─ 未命中：查询 PostgreSQL → 写入 Redis → 返回
```

Redis 读取失败、JSON 损坏或写入失败时，系统记录警告并继续使用 PostgreSQL。

为防止热门通道缓存失效后击穿数据库，同一应用实例按 `channelCode` 使用独立加载锁，并在获得锁后再次检查缓存。20 个并发请求测试中，数据库 Mapper 只执行一次。

当前加载锁只合并单个 JVM 内的请求。多实例场景仍可能每个实例各查询一次数据库，但不会影响业务正确性。

## 7. 幂等结果缓存

创建交易前先按幂等键读取 Redis：

```text
缓存命中 → 返回第一次交易结果
缓存未命中 → 尝试插入 PostgreSQL
数据库唯一键冲突 → 按幂等键查询原交易
→ 回填 Redis → 返回原交易
```

因此 Redis 只加速重复请求，最终幂等性由 PostgreSQL 唯一约束保证。

交易状态变化后删除对应幂等缓存。下次请求回源 PostgreSQL 获取最新状态，再重新写入缓存，实现最终一致性。

## 8. Lua 原子操作

本项目在以下场景使用 Lua：

- 请求计数并设置窗口过期时间；
- 通道额度“检查后扣减”；
- 风控窗口“清理、写入、统计、判断”；
- 分布式锁按 token 安全释放。

Lua 的作用是让一组 Redis 命令不可被其他请求插入执行。它只能保证 Redis 内部操作原子，不能让 Redis 和 PostgreSQL 形成一个共同事务。

## 9. 分布式锁

获取锁使用带租期的 `SET NX`，锁值是每个持有者独有的 UUID token。释放锁使用 Lua：只有 Redis 中的 token 与当前持有者一致时才删除。

故障实验证明：

```text
持有者 A 获得锁
→ A 业务尚未完成，但锁租期结束
→ 持有者 B 获得新锁并进入
→ A 和 B 可能同时执行
```

token 能防止 A 误删 B 的锁，但不能阻止租期过期后的并发执行。因此交易正确性仍依赖：

- 幂等键和数据库唯一约束；
- 状态机；
- `version` 乐观锁；
- 数据库事务。

## 10. 降级策略

| 功能 | Redis 不可用时的策略 | 原因 |
|---|---|---|
| 用户请求限流 | 放行并记录警告 | 可用性优先，数据库规则继续保护正确性 |
| 通道路由缓存 | 回源 PostgreSQL | 缓存可重建 |
| 幂等结果缓存 | 回源数据库唯一约束 | PostgreSQL 是最终幂等保障 |
| 通道额度 | 高风险生产场景建议拒绝或走数据库校验 | 防止通道额度被快速打穿 |
| 风控窗口 | 根据风险等级拒绝、降额或转人工 | 不应默认绕过高风险控制 |
| 分布式锁 | 不把锁作为唯一正确性前提 | Redis 不可用或锁过期都可能失去互斥 |

不同功能不能统一使用“全部放行”或“全部拒绝”。降级选择取决于故障后的资金风险和可用性要求。

## 11. 已验证场景

- 第 11 次用户请求返回 429；
- 通道额度超限时计数不变；
- 并发额度扣减不超过上限；
- 风控窗口按次数和金额拒绝；
- 路由缓存第二次查询不访问数据库；
- 20 个并发缓存未命中只查询一次数据库；
- 幂等缓存命中返回原交易；
- 缓存被删除后由数据库唯一约束恢复原交易；
- Redis 完全不可用时交易仍能创建并保持幂等；
- 状态更新后旧缓存删除并重新加载；
- 分布式锁过期后第二个持有者能够进入；
- 旧持有者不能删除新持有者的锁。

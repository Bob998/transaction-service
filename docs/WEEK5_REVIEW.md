## 关键知识

### 1. Redis 不是最终账本

Redis 适合保存可过期、可重建的数据。交易金额、最终状态、审计日志和 Outbox 仍保存在 PostgreSQL。即使 Redis 数据全部丢失，也不应丢失最终交易事实。

### 2. Lua 解决什么问题

`GET` 后再 `SET`、判断额度后再 `INCRBY` 都可能被并发请求插入。Lua 将多条 Redis 命令组成一次原子执行，解决 Redis 内部的竞态条件。

Lua 不能保证 Redis 与 PostgreSQL 同时提交，也不能替代数据库事务。

### 3. 金额为什么转换成分

浮点数无法精确表示许多十进制金额。额度计算使用：

```text
BigDecimal 10.25 元 → long 1025 分
```

这样 Redis 只进行整数加法，避免金额累计误差。

### 4. Cache-Aside

读取时先查缓存，未命中再查数据库并回填；更新时先更新数据库，再删除缓存。缓存和数据库之间不存在共同事务，因此系统追求最终一致性，而不是把 Redis 当作强一致存储。

### 5. 缓存击穿

热门 Key 过期后，大量请求可能同时访问数据库。本项目通过按通道编码的加载锁和双重检查，把同一 JVM 内的并发数据库查询合并成一次。

当前方案不保证多实例之间只查一次，但即使重复查询数据库，也只影响性能，不影响交易正确性。

### 6. 分布式锁过期

锁有租期才能避免永久死锁，但租期可能早于业务执行结束。旧持有者与新持有者会同时执行，所以分布式锁不能作为唯一安全边界。

释放锁必须比较 token 后删除，避免旧持有者删除新持有者的锁。

### 7. 降级不是统一放行

- 普通接口限流失败可以放行；
- 缓存失败可以回源数据库；
- 幂等缓存失败可以依靠唯一约束；
- 风控和通道额度失败时需要根据资金风险选择拒绝、数据库校验或人工处理。

## 故障实验结果

### Redis 不可用

模拟所有 Redis 访问抛出连接异常。第一次请求仍由 PostgreSQL 创建交易，第二次重复请求由数据库唯一约束找到原交易，两次返回相同交易 ID。

### 缓存击穿

20 个线程同时查询一个未缓存热门通道。第一个线程回源数据库，其余线程等待并读取回填缓存，数据库 Mapper 只调用一次。

### 分布式锁过期

第一个持有者获得 100 毫秒租期的锁。300 毫秒后第二个持有者成功进入，证明锁过期不代表旧业务结束。token 释放脚本阻止旧持有者误删新锁。

### 数据库与缓存暂时不一致

交易从 `CREATED` 更新为 `RISK_APPROVED` 后删除旧幂等缓存。后续重复请求回源 PostgreSQL，读取最新状态并重新缓存。

## 当前边界与后续改进

- 当前请求限流依赖演示用 `X-User-Id`，正式系统应从认证信息获取用户身份；
- 通道额度和风控窗口已接入交易创建流程；后续可在实际支付编排中增加额度释放、退款和补偿逻辑；
- 缓存击穿锁当前只覆盖单个 JVM，多实例可使用短租期分布式协调或异步刷新；
- 热 Key 可通过本地缓存、Key 分片、只读副本和请求合并继续优化；
- 风控和额度的 Redis 故障策略应通过配置按业务风险等级切换；
- 状态更新后的缓存删除属于最终一致性，生产系统可结合 Outbox 异步重试缓存失效。
